# ADR 0007 — v3.0 revision-loop protocol (mutation semantics, re-post format, debounce, revision/approval concurrency, cost-cap pause/resume)

- **Status:** Accepted (revision protocol ratified 2026-07-24, bead `xm4`; cost-cap pause/resume ratified 2026-07-24, bead `3e8`; ADR written 2026-07-25 — v3.0 implementation deferred just-in-time, no code lands yet)
- **Date:** 2026-07-25
- **Owner:** Backhaus
- **Relates to:** Meal Planner Bot design doc v1.0, §7 (Slack UX — thread-per-week, multi-person feedback, approval commands), §9.3 (cost control — revision's three nested guards: ≈150K tokens/cycle, ≈25 turns/thread, ≈$5/thread). **Builds on** ADR 0002 (session row, `under_revision` state, write-before-post transition discipline) and ADR 0003 D5 (deterministic post-validation with one bounded repair retry — reused here for revised plans). **Pairs with** ADR 0006 (the Todoist commit that `/mealplan-approved` triggers, and the `working_plan` this protocol mutates). Resolves beads `xm4` and `3e8`.

---

## Context

ADR 0002 names the `under_revision` session state and the `suggested → under_revision → committed` transitions, but specifies none of the mechanics a live thread reply needs:

1. **Mutation semantics.** Does a reply trigger a full re-selection over the recipe pool, or a targeted change to the existing `working_plan`?
2. **Re-validation and re-post format.** Is a revised plan re-checked the way ADR 0003 D5 checks the original? Does it edit the existing Slack message or post a new one?
3. **Batching.** "The family" is plural (SPEC §7) — rapid, possibly-conflicting replies need some debounce/batch discipline, not one LLM call per message.
4. **Revision vs. approval concurrency.** What happens when `/mealplan-approved` arrives while a revision is in flight — which `working_plan` version commits?
5. **Cost-cap aftermath.** SPEC §9.3's revision caps (150K tokens/cycle, 25 turns/thread, $5/thread) are concrete numbers, but the recovery half was unspecified: does generation spend count against the same budget as revision; can a paused thread resume itself; does approval still work while paused; is "paused" a real state or just a log line?

Both decisions gate v3.0 Socket Mode work and were ratified together (`xm4`, `3e8`) on 2026-07-24. This ADR is the durable record of the ratified protocol — no new decisions are made here.

---

## Decision

### D1 — A reply triggers a bounded LLM revision that mutates the current `working_plan`, not a blind full re-selection

An inbound thread reply runs a single bounded LLM call scoped to the session row's *current* `working_plan` (the ADR 0002 `working_plan` JSON) as its starting point, not a fresh `search_recipes` → select pass over the whole pool. The model is asked to apply the requested change(s) to the existing plan. This keeps a revision cheap (bounded by the per-cycle token cap, SPEC §9.3) and keeps unrelated meals stable across a reply that only touches one slot — re-selecting from scratch could silently swap meals nobody asked to change.

### D2 — Revised plan is re-validated via ADR 0003 D5 and re-posted as a new thread message; never edited in place

The revision output runs through the **same** deterministic validation + one-shot repair retry as initial generation (ADR 0003 D5) — correct counts, real `recipe_id`s, veg-path consistency, no within-week repeats. On success, the revised plan is posted as a **new reply in the existing thread** (`chat.postMessage` with `thread_ts` set to the week's parent `ts`), never an edit (`chat.update`) of a prior message. Append-only preserves the full audit trail in-thread and keeps the v3.0 late-reply/reverse-map mechanics (ADR 0002 D5, `idx_session_thread_ts`) intact — an edited message would erase the history of what was proposed and when. The session row's `working_plan` is updated to the revised version after the post succeeds (mirrors ADR 0002 D2's write-after-post-succeeds ordering for the original draft).

### D3 — Rapid replies are debounced into one revision per burst

Multiple family replies arriving in quick succession are **not** each dispatched as a separate LLM call. They are batched by a debounce window and folded into a single revision call that reasons over all pending messages together (consistent with SPEC §7's "the bot folds all in-thread messages into revision context ... rather than assuming a single instruction"). This bounds both cost (fewer cycles against the per-thread turn/token caps, §9.3) and the risk of two overlapping revisions racing each other. The exact debounce window is a v3.0 implementation detail (Open items).

### D4 — Single-writer serialization on the session row; approval supersedes any in-flight revision

The session row is single-writer: only one revision or approval operation is in flight against a given row at a time. When `/mealplan-approved` arrives while a revision cycle is in flight, **approval wins** — it commits the row's *current* `working_plan` (whatever the last successfully-validated-and-posted version is) under the existing ADR 0002 transition discipline, and ends the revision loop. Approval is preferred as the tie-breaker because it costs nothing and terminates the loop deterministically; an in-flight revision does not block or delay approval.

### D5 — Generation and revision share one per-thread cost budget

The SPEC §9.3 revision caps (per-cycle token cap ≈150K, per-thread turn cap ≈25, per-thread cumulative budget ≈$5) are **not** revision-only — the initial generation spend for that week's thread counts against the same per-thread pool. There is one budget per thread, not a separate generation allowance plus a separate revision allowance. Rationale: the real risk SPEC §9.3 names is a runaway *revision* loop (an event-driven listener calling a paid API on every inbound message), and a single shared pool is the simplest guard against it — splitting the budget would let a cheap generation "reset" headroom that revision could then exploit.

### D6 — A cost-cap pause is a real session-state transition, reset only by an explicit operator command

Hitting any of the three §9.3 caps on a thread **pauses** that thread: this is a state on the ADR 0002 session row, not merely a log entry or alert. Per SPEC §9.3, hitting a cap already means "stop, alert `#agent-alerts`, and post an in-thread 'paused for cost' note" — D6 makes that stop durable and queryable rather than transient. A paused thread is **never auto-resumed** (not by the next scheduler tick, not by a subsequent reply) — only an explicit operator command clears the pause. The exact command surface (CLI flag, Slack admin command, manual row edit) is a v3.0 implementation detail (Open items).

### D7 — Approval is always allowed while paused

`/mealplan-approved` on a paused thread is honored unconditionally — it commits the current `working_plan` exactly as D4 describes for the in-flight-revision case, costs nothing, and ends the loop. A cost pause blocks further *generation/revision* spend on the thread; it never blocks committing what's already there.

## Interface sketch

```ts
// D1/D2 — revision reuses ADR 0003's validate+repair; posts new, never edits
async function reviseForWeek(wk: WeekKey, incomingReplies: SlackMessage[]) {
  const row = getSession(wk);                                  // single-writer: acquire row lock
  if (row.status === "paused_cost") return;                    // D6 — no auto-resume
  if (isApprovalInFlight(wk)) return;                          // D4 — approval supersedes revision

  let plan = mutate(row.working_plan, incomingReplies);        // D1 — LLM mutation, not re-selection
  let errs = validate(plan, row.pools, cfg);                   // ADR 0003 D5, reused as-is
  if (errs.length) {
    plan = llmSelect(buildRepairPrompt(plan, errs));
    errs = validate(plan, row.pools, cfg);
    if (errs.length) throw new PlanValidationError(errs);
  }

  const ts = slack.postMessage(cfg.channelId, renderRevision(plan), { thread_ts: row.thread_ts }); // D2 — new msg
  updateSession(wk, { status: "under_revision", working_plan: plan });   // write after post succeeds
}

// D5/D6 — one shared budget per thread; pause is a row state, cleared only by operator command
interface SessionCostFields {
  turn_count: number;    // generation + all revision cycles share this counter (D5)
  token_spend: number;   // per-cycle cap (~150K) checked per call; cumulative checked against $ cap
  cost_usd: number;
  status: "generating" | "suggested" | "under_revision" | "paused_cost" | "committed" | "failed" | "expired";
}

function onCapHit(wk: WeekKey) {
  updateSession(wk, { status: "paused_cost" });        // D6 — durable state, not just a log line
  slack.postMessage(cfg.channelId, "paused for cost", { thread_ts: getSession(wk).thread_ts });
  alert(`#agent-alerts: week ${wk} revision paused for cost`);
}

// D7 — approval always allowed, even while paused
function onApprovalCommand(wk: WeekKey) {
  const row = getSession(wk);                          // paused_cost included — no special-case block
  commitToTodoist(row.working_plan);                    // ADR 0006
  updateSession(wk, { status: "committed" });
}
```

## Alternatives considered

- **Full re-selection on every reply** — rejected (D1). Re-running `search_recipes` → select from scratch risks silently changing meals the family didn't ask to touch, and costs more per turn than a scoped mutation.
- **Edit the existing Slack message in place on revision** — rejected (D2). Destroys the in-thread audit trail and complicates the v3.0 late-reply reverse-map (which keys off distinct posted `ts` values); appending a new message is strictly additive.
- **Skip validation on revision (trust the mutation)** — rejected (D2). The whole point of ADR 0003 D5's hard-guarantee design is deterministic checks on every LLM output that becomes `working_plan`; a revision path is not exempt.
- **One LLM call per inbound reply (no debounce)** — rejected (D3). "The family is plural" (SPEC §7) means rapid multi-reply bursts are expected; per-message dispatch burns turn-cap budget fast and risks two revisions racing on the same row.
- **Revision wins over an in-flight approval (or: block approval until revision completes)** — rejected (D4). Approval is free and terminal; making it wait on a paid LLM call it doesn't need is the wrong tradeoff, and a race where "whichever finishes first" wins is nondeterministic.
- **Separate cost pools for generation vs. revision** — rejected (D5). SPEC §9.3 already names runaway *revision* as the real risk; a split budget would let cheap generation spend "free up" room revision could then burn through, defeating the point of a hard per-thread ceiling.
- **Auto-resume a paused thread** (next scheduler tick, or on the next reply) — rejected (D6). Silently resuming paid spend after a human-attention event (a cost cap trip) is exactly the runaway-loop risk SPEC §9.3 flags; mirrors ADR 0002 D4's "stale `generating` row" precedent of alert-then-require-a-human, not auto-heal.
- **Block `/mealplan-approved` while a thread is paused for cost** — rejected (D7). Approval doesn't spend anything and is the cleanest way to end a stuck loop; blocking it would leave a paused thread with no exit but an operator reset.

## Consequences

**Positive**
- **Cheap, targeted revisions.** Mutating the existing plan instead of re-selecting keeps a typical revision cycle small relative to the ≈150K-token per-cycle cap, and stable meals stay stable across unrelated edits.
- **Full audit trail.** Append-only re-posting means every proposed revision is visible in-thread forever, and feeds the same `ts`-keyed reverse map ADR 0002 already built for late-reply recognition.
- **Deterministic concurrency.** Single-writer serialization plus "approval always wins" removes the ambiguous case ADR 0002 left open (which `working_plan` commits) with one simple rule, and it's the cheap outcome (approval costs nothing).
- **One well-understood guard against the real risk.** A single shared per-thread budget (D5) directly targets SPEC §9.3's stated concern — runaway revision — without adding a second budget to reason about.
- **Cost pauses are recoverable but never silent.** D6/D7 give a stuck thread exactly two exits — an explicit operator reset, or approval — both intentional acts, never an automatic retry that could compound a runaway.

**Tradeoffs / risks**
- **Debounce adds latency.** A family expecting a near-instant reply-to-revision turnaround will wait out the debounce window; the exact window is a tuning knob (Open items), not fixed here.
- **A paused thread with no operator around stays paused.** By design (D6) — but if nobody is watching `#agent-alerts`, a mid-week revision loop stalls until someone acts (or the family approves what's already posted, per D7).
- **Mutation-not-reselection can get stuck in a local optimum.** If a reply asks for a change the current plan structurally can't accommodate via mutation (e.g., a wholesale week redo), the bounded mutation call may repeatedly fail validation; the existing D5-style one-shot repair retry is the only automatic recourse before it alerts and fails the cycle (ADR 0003 D5 semantics, reused as-is).
- **Shared budget means a big generation eats into revision headroom for that week.** Accepted per D5 — the alternative (split pools) was judged to reintroduce the risk this design closes.

## Open items (non-blocking; resolved just-in-time before v3.0 build)

- **Exact debounce window** (D3) — how long to wait after a reply before dispatching the batched revision call; a tuning value, not fixed here.
- **Operator-reset command surface** (D6) — CLI flag, Slack admin command, or direct row edit to clear `paused_cost`; mechanism is v3.0 implementation detail.
- **Who may issue `/mealplan-approved`** (SPEC §7 TODO, §10.2) — still open, orthogonal to this ADR; D4/D7 govern *what happens* on approval, not *who* may trigger it.
- **Late-reply-to-expired-thread UX** (ADR 0002 Open items) — still open; this ADR's debounce/mutation logic applies only to replies on the *active* thread (SPEC §7 listener scope).
